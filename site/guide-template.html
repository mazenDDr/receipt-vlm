Field guide

Teaching a 3B model to read receipts, and finding out what that costs

Every part of the system, with the measurement that decided it. Fine-tuning moved field F1 from 0.440 to 0.836 on receipts the model had never seen. Quantizing to 4 bits cost nothing measurable. Two of the most convincing results along the way turned out to be bugs in the pipeline, and both are here too.

01 · Data

1,000 receipts, split so nothing leaks

CORD v2 is 1,000 photographed Indonesian till receipts, each labelled with its fields as JSON. The published split is 800 / 100 / 100. Before using it, every image was hashed perceptually and compared across splits: 28 near-duplicate images appeared in more than one split and were dropped, leaving 773 / 99 / 100. Choices are made on dev; the test split was scored once.

src/receipt_vlm/data/build.py data/dedup.py scripts/build_data.py configs/data.yaml
Why a perceptual hash, not an exact one. The same receipt appears in CORD more than once at different crops and compressions, which an exact hash misses entirely. A 256-bit difference hash caught 28 of them. Without that check the test scores would have been measured partly on receipts the model trained on.

02 · Fine-tuning

QLoRA on one consumer GPU

The base model is loaded in 4-bit NF4 with the vision tower kept in bf16, and LoRA adapters are trained on the language model only. Loss is computed on the answer tokens alone. The whole run fits in 16 GB of VRAM.

train/qlora.py train/collate.py train/sweep.py prompts.py
Why the language model only. Adapting the vision projector as well was one arm of the ablation and did not help: 0.867 against 0.900 on dev. Rank 8 and rank 32 both scored below rank 16, and partial full fine-tuning of the last four layers scored 0.817. The full table is in docs/ablations.md.

03 · Quantization

Four bits costs nothing here. Below four, it depends on calibration.

The adapter is merged into bf16, then quantized two ways: AWQ W4A16 for vLLM, and seven GGUF bit widths for llama.cpp. Everything from Q8_0 down to Q4_K_M sits within noise of the bf16 reference, and each is faster.

Why the vision projector has to be f32. Built at f16 it overflows into NaN on particular receipts and the model emits ! until it hits the token cap — silently, with the server reporting normal throughput. It cannot be quantized either, so it is a fixed 2.49 GiB on every GGUF row, which is why no GGUF build undercuts the AWQ checkpoint on disk.

04 · What is still wrong

The model reads receipts well and misfiles what it reads

All 100 held-out receipts produced valid JSON — there are no format failures. Reading the worst twenty by hand against their photographs, and then counting every pattern found that way across the whole dev split, gives a different picture from the aggregate score.

Why this points away from more data. The worst receipt in the split has every value correct and every key wrong. Separator conventions alone account for about a third of the numeric gap. Neither is fixed by more training examples; both are decisions about CORD's schema, which is what constrained or schema-aware decoding addresses. The conventions themselves are written up in docs/annotation_guidelines.md.

05 · Serving

One image in, its fields out, with what the answer cost

The API calls the same backend registry the evaluation does, so one service can front transformers, vLLM or llama.cpp by changing two lines of config. Every response carries the latency, token counts and throughput that the deployment decision was made on.

serve/api.py serve/gradio_app.py infer/backends.py Dockerfile
There is no hosted demo. Running a 3B vision model costs money, and a free CPU tier would serve it at a few tokens per second — a poor advertisement for something that runs at 103 tokens per second on a GPU. The recorded extractions show every held-out receipt instead, and the README documents running it locally.
